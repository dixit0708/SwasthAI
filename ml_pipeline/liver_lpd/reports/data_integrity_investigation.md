# Liver Disease Model (Lab-Based / LPD) — Data Integrity Investigation

**Status: investigation only. Nothing here is wired into the backend or
frontend yet.** `train.py` has produced `artifacts/liver_lpd_pipeline_v1.pkl`
and `artifacts/liver_lpd_metadata_v1.json` on disk, but no code anywhere in
`backend/` loads or serves them, and no frontend page references them.
This report exists so a decision about which model (if any) to actually
ship can be made with full evidence in hand, before any of that wiring
happens.

## Why this needed stopping for

The task was: train a lab-based liver-disease model on a user-provided
dataset, achieving at least 95% accuracy. Two of the three model families
tried **did** clear that bar — by a wide margin. But the specific way they
cleared it is a textbook data-integrity red flag, not a genuine result, and
shipping it uncritically would violate this project's own rule (AGENTS.md
Section 9: "never fabricate or artificially improve metrics") even though
no one intentionally engineered the number — the dataset itself appears to
make it happen.

## Evidence

### 1. The raw file is 37% exact duplicate rows

`Liver Patient Dataset (LPD)_train.csv` (30,691 rows, 11 columns, schema
matching the classic ILPD panel) contains **11,323 fully duplicate rows
(36.9%)**. This alone is unusual for organically collected clinical data —
real patient records don't duplicate at this rate — and is a known,
previously-flagged property of this specific extended ILPD mirror
circulating online. All duplicates were dropped **before** any split (see
`data/raw/README.md`, `preprocessing.py`), leaving 16,389 clean rows used
for everything below.

### 2. Ruled out: near-duplicate "bootstrapped patient" leakage

The first hypothesis was that the 30,691 rows were generated by repeating
a much smaller set of real patients with tiny numeric jitter — duplicates
just under the exact-match threshold, which would still leak information
across train/test splits even after dropping exact duplicates. This was
tested directly: rounding every numeric feature to the nearest whole
number and clustering rows found **16,385 distinct clusters out of 16,389
rows** — essentially no near-duplication survives dedup. **This hypothesis
was rejected by the data.**

### 3. A large, model-family-dependent accuracy gap

5-fold cross-validation (train+val, test set untouched), same methodology
used for every other model in this project:

| Model | CV ROC-AUC | CV F1 | CV Recall | CV Accuracy |
|---|---|---|---|---|
| Logistic Regression | 0.7621 | 0.6816 | 0.5430 | 0.6364 |
| Random Forest | 0.9996 | 0.9995 | 0.9996 | 0.9993 |
| XGBoost | 0.9995 | 0.9998 | 0.9999 | 0.9997 |

Logistic Regression's 0.76 ROC-AUC sits squarely in the range published
literature reports for linear models on ILPD-family data (this project's
own retired `liver-ilpd-v1`, on the small 583-row original, and
`liver-nhanes-v1` both land in a similar 0.73-0.76 band). The jump to
essentially perfect separation for tree ensembles specifically — not a
modest improvement, but 0.24 ROC-AUC points, landing at 0.9996 — is the
first red flag: real biological/diagnostic noise does not usually vanish
just because a more flexible model family was used.

### 4. No single feature is a trivial giveaway

Checked in case one column alone (near-)encoded the label:

| Feature | Single-feature ROC-AUC |
|---|---:|
| total_bilirubin_mg_dl | 0.703 |
| aspartate_aminotransferase_u_l | 0.701 |
| direct_bilirubin_mg_dl | 0.696 |
| alanine_aminotransferase_u_l | 0.687 |
| alkaline_phosphatase_u_l | 0.670 |
| albumin_g_dl | 0.389 |
| albumin_globulin_ratio | 0.379 |
| total_proteins_g_dl | 0.476 |
| age_years | 0.504 |

All in a plausible, realistic range for individual liver-panel markers —
nothing here explains a jump to 0.9996 on its own. The separability has to
come from how the tree ensembles combine features.

### 5. The decisive test: does a single, unpruned decision tree also hit ~100%?

If a single decision tree (no ensembling, no randomness, easy to inspect)
can also achieve near-perfect test accuracy, that means the label is a
**near-deterministic function of the input features** — the kind of
relationship you get from a rule-based label-generation process, not from
noisy real-world diagnosis. Tested directly, at increasing tree depth:

| Max depth | Test accuracy | Test ROC-AUC | Leaves |
|---:|---:|---:|---:|
| 2 | 0.7175 | 0.7351 | 4 |
| 3 | 0.7175 | 0.7650 | 7 |
| 4 | 0.7422 | 0.7876 | 12 |
| 6 | 0.7816 | 0.8551 | 29 |
| **unlimited** | **1.0000** | **1.0000** | 140 |

**A fully-grown single decision tree gets literally 100.00% test
accuracy and ROC-AUC 1.0000 on held-out data it never trained on.** This
essentially never happens with genuine clinical outcomes from a 9-feature
lab panel — real patients have overlapping, ambiguous cases (borderline
values, comorbidities, measurement noise) that no amount of tree depth
resolves perfectly. Getting exactly zero test errors at 140 leaves is the
signature of a deterministic or near-deterministic generating rule that a
sufficiently deep partition of feature space can fully recover.

The depth-3 tree (still realistic, 76.5% ROC-AUC) shows the kind of
structure you'd expect from real clinical thresholds (bilirubin, ALT,
ALP cutoffs) — the anomaly only appears once the tree is allowed to grow
deep enough to carve out increasingly specific, low-population regions
that apparently correspond 1:1 with individual label values in this
specific file.

## Conclusion

The evidence points to the 30,691-row "Liver Patient Dataset (LPD)" file
having a label that is synthetically or rule-derived (or otherwise
near-deterministic) rather than reflecting the natural diagnostic noise of
a genuine large patient cohort. This is **not** the standard train/test
leakage this project usually guards against (no patient ID or duplicate
row crosses a split boundary here — that was checked and ruled out
directly). It looks like a property of the dataset's origin, most likely
some kind of expansion/augmentation applied to the original small (583-row)
ILPD release.

**Reporting the Random Forest / XGBoost numbers (99%+ accuracy, ROC-AUC
~1.0) as this model's real-world screening performance would be reporting
a dataset artifact as if it were genuine predictive power** — exactly what
AGENTS.md Section 9 exists to prevent, regardless of intent. The Logistic
Regression result (ROC-AUC 0.76, consistent with every other lab-adjacent
model already shipped in this project) is far more likely to reflect how
this kind of model actually performs on real patients.

## What is on disk right now

- `artifacts/liver_lpd_pipeline_v1.pkl` / `liver_lpd_metadata_v1.json` —
  the **Random Forest** pipeline `train.py` selected by CV ROC-AUC (the
  metric that made it look best is exactly the metric this report
  disputes). **Not loaded by the backend. Not referenced by any frontend
  page.** Exists only as the direct output of the run described above.
- No `backend/app/ai/models/liver_lpd_model.py`, no new prediction
  endpoint, no new frontend pages have been created yet — that work was
  intentionally paused pending this decision.

## Options going forward (no default has been chosen)

1. **Ship Logistic Regression instead.** Retrain selecting on CV ROC-AUC
   among only models whose depth-limited behavior looks realistic, and
   proceed with the ~76% ROC-AUC result — consistent with every other
   model in this project, but does not hit the requested 95% accuracy,
   and that would need to be stated plainly rather than worked around.
2. **Ship the Random Forest/XGBoost result anyway, heavily disclosed** —
   not recommended for a project that positions itself as a real
   healthcare product; the ~99% number would need a prominent caveat
   everywhere it appears (docs, metadata, any UI surface), and it would
   likely not survive scrutiny from anyone who re-derives it.
3. **Don't ship a lab-based liver model from this dataset at all** —
   keep `liver-nhanes-v1` (lab-free) as the only liver assessment for now,
   and look for a dataset with better-documented, verifiably real-patient
   provenance before building this second option.
4. Something else — e.g. attempting to source the original, small,
   well-documented 583-row ILPD release (already used once for the retired
   `liver-ilpd-v1` in `ml_pipeline/liver/`) as the lab-based option instead
   of this larger, suspect file.
